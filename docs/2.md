# Vildly — спецификация разработки MVP

| Поле | Значение |
|---|---|
| Статус | Draft для согласования |
| Цель | Безопасный стабильный Telegram MVP на PostgreSQL |
| Вне цели | RAG, Discord и MCP в рамках этой спецификации |

## Цель

Стабилизировать текущий прототип без переписывания: защитить персональные данные, закрепить схему миграциями, завершить Telegram UX и добавить автоматические проверки. После этого проект готов к отдельному этапу RAG.

## Scope

Входит:

1. Secrets/configuration.
2. Alembic и DB constraints.
3. Auth для API и SQLAdmin.
4. Завершение текущих Telegram buttons/FSM.
5. Pydantic API schemas.
6. Unit, integration, API и bot tests.
7. DB healthcheck и lifecycle.
8. Согласованная очистка SQLite legacy.

Не входит: RAG pipeline, Discord, MCP, payments, CRM, LMS, новый frontend.

## Функциональные требования

### FR-01. Регистрация #DONE

- Принимать только Telegram contact текущего пользователя.
- Валидировать и нормализовать phone/email.
- Не допускать один email у разных `telegram_id`.
- Повторный update не создаёт дубль.
- Ошибка валидации не меняет БД.
- Повторный `/login` зарегистрированного пользователя безопасен.

Приёмка: конкурентная регистрация одинакового email создаёт максимум одну запись; все ветки покрыты tests.

### FR-02. Telegram UX #DONE

Статус: реализовано.

- `Back` показывает `command_keyboard` зарегистрированному пользователю, `main_keyboard` — гостю.
- Каждая показанная inline button имеет handler и вызывает `callback.answer()`.
- Неготовый курс отвечает «в разработке», а не зависает.
- `Book a Lesson` показывает placeholder: «🚧 Запись на занятия находится в разработке.»

### FR-03. User API

Статус: реализовано через Bearer token `API_TOKEN`.

- Добавить Pydantic response schemas.
- `/users` и `/users/{telegram_id}` доступны только авторизованному оператору.
- Публичные ответы не содержат phone/email.
- 404 и auth errors имеют стабильную схему.

### FR-04. SQLAdmin

- `/admin` защищён authentication backend.
- Session secret приходит из environment.
- Набор отображаемых PII-полей согласован.
- Production credentials не имеют defaults в коде.

### FR-05. Миграции

- Добавить Alembic и initial migration.
- Добавить unique constraint/index на нормализованный email.
- Новые schema changes выполняются миграциями.
- `create_all()` не используется как production migration mechanism.

Приёмка: пустая БД обновляется до Alembic head; приложение стартует на head.

### FR-06. Конфигурация

- `TOKEN`, `DATABASE_URL`, admin secret и credentials поступают из environment/secrets.
- Compose не содержит production passwords.
- `.env.example` содержит только безопасные placeholders.
- Ошибка конфигурации называет переменную, но не раскрывает значение.

### FR-07. Lifecycle

- PostgreSQL имеет healthcheck.
- Bot/API ждут healthy DB.
- Engines закрываются на shutdown.
- Compose сохраняет отдельные процессы `api` и `bot`.

## Нефункциональные требования

| ID | Требование |
|---|---|
| NFR-01 | PII недоступна без auth |
| NFR-02 | Secrets и PII не попадают в logs |
| NFR-03 | Email uniqueness обеспечивается PostgreSQL |
| NFR-04 | Unit tests не требуют внешних сервисов |
| NFR-05 | Integration tests используют только test DB |
| NFR-06 | `docker compose up` проходит cold start |
| NFR-07 | Python >=3.11; Docker reference Python 3.13 |

## Этапы

1. Baseline: воспроизводимые unit/integration tests и smoke imports.
2. Data integrity: Alembic, initial migration, unique email, concurrency test.
3. Security: auth, response schemas, PII boundary tests.
4. Telegram UX: Back, callbacks, Book a Lesson decision, handler tests.
5. Runtime: healthcheck, shutdown, external secrets, Compose verification.
6. Legacy: проверить необходимость `data/users.db`, затем убрать ненужные SQLite dependencies/docs.

## Тестовая стратегия

- Unit: validators, normalization, `RegistrationService`, keyboard selection.
- Integration: repository, constraints, Alembic upgrade, concurrent duplicate.
- API: auth, 200/404, response schemas, SQLAdmin boundary.
- Bot: FSM happy/error paths, foreign contact, Back, all callbacks.
- Runtime: Compose config, cold start, restart persistence, graceful shutdown.

## Definition of Done

- Все согласованные требования проверяются автоматически или имеют manual verification.
- Unit, integration, API и bot suites проходят.
- Alembic upgrade до head проходит на пустой PostgreSQL.
- Compose поднимает healthy DB, API и bot.
- Неавторизованный клиент не читает PII.
- Нет кнопок без handlers и secrets в Git.
- `AGENTS.md`, `docs/1.md`, `docs/2.md`, `.env.example` соответствуют коду.
- RAG/Discord/MCP не добавлены без отдельной согласованной спецификации.

## Требуют решения

1. Auth mechanism для API и SQLAdmin.
2. Политика хранения, удаления и маскирования phone/email.
3. Нужно ли сохранять `Book a Lesson` в БД.
4. Какие курсы входят в MVP.
5. Нужна ли миграция данных из `data/users.db`.
6. Нужен ли внешний User API или достаточно SQLAdmin.
7. Production platform и способ передачи secrets.
8. Начинается ли RAG только после стабилизации MVP.
